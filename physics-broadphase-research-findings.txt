1.1 Datenstrukturen, die PhysicsSystem fuer Bodies/Collider haelt
--------------------------------------------------

PhysicsSystem.ts:17-18:

  private _bodies: Object3D[] = [];
  private _allColliders: Object3D[] = [];

Beides sind PLAIN ARRAYS aus Object3D, keine separate RigidBody[]/StaticCollider[]
Sammlung, und nicht oeffentlich exponiert (kein Getter). _warnedObjects ist ein
Set<Object3D> (Zeile 25), nur genutzt, um eine Console-Warnung zu deduplizieren.

Es gibt KEINE addBody()/addCollider()-API ueberhaupt. Die Arrays sind privat und
werden JEDEN einzelnen step()-Aufruf komplett neu aufgebaut, indem scene.objects
(also scene.root.children, Scene.ts:21-23) rekursiv durchlaufen wird:

- Bodies: _collectBodiesRecursive (PhysicsSystem.ts:30-45), aufgerufen aus step()
  (Zeilen 56-61: bodies.length = 0, dann rekursiver Walk). Ein Knoten qualifiziert
  sich als "Body", wenn obj.isCollidable && obj.rigidBody &&
  obj.rigidBody.inverseMass > 0 (Zeilen 31-33) - d.h. NUR dynamische
  (nicht-statische) Rigidbodies landen in _bodies. Statische/kinematische Bodies
  (inverseMass === 0, Masse 0) werden aus _bodies ausgeschlossen, zaehlen aber
  trotzdem als Collider.

- Collider: _collectCollidersRecursive (Zeilen 153-160), aufgerufen aus
  _resolveCollisions (Zeilen 164-169). Ein Knoten qualifiziert sich, wenn
  obj.isCollidable && obj.bounds (Zeile 154) - das schliesst SOWOHL dynamische ALS
  AUCH statische Objekte ein, und durchlaeuft den kompletten Szenengraph ein
  ZWEITES Mal pro Frame.

- Die tatsaechliche "Registrierung" ist also: Aufrufer pushen beliebige Object3D
  ueber scene.add(...) (Scene.ts:42-44 -> Object3D.add, Object3D.ts:56-62), und
  PhysicsSystem entdeckt jeden einzelnen Frame per zwei volle rekursive
  Baum-Durchlaeufe neu, wer kollidierbar ist. Es gibt keine persistente
  Registrierungsliste, die ein Aufrufer pflegt - die Arrays sind transiente
  Scratch-Buffer, die Frame fuer Frame wiederverwendet werden (bestaetigt durch
  tests/physix/ZeroAllocation.test.ts:59-90, das genau die Instanz-Identitaet von
  _bodies/_allColliders/_collisionEvent ueber mehrere step()-Aufrufe hinweg
  prueft).

- StaticCollider (src/physix/StaticCollider.ts:8-17) ist eine separate,
  leichtgewichtige Klasse, die Collidable implementiert (nur bounds +
  isPickable) - aber PHYSICSSYSTEM REFERENZIERT STATICCOLLIDER NIRGENDS (kein
  Import, kein Type-Check). Sie scheint dafuer gedacht zu sein, direkt in
  SpatialHash/Octree eingefuegt zu werden (beide nehmen Collidable), am
  Object3D-basierten Sammel-Mechanismus von PhysicsSystem komplett vorbei. Das ist
  eine Verdrahtungsluecke: heute muessen statische Hindernisse volle Object3Ds mit
  rigidBody = new RigidBody(0) sein (siehe Warnung PhysicsSystem.ts:34-39), um von
  _resolveCollisions erfasst zu werden; ein blankes StaticCollider-Objekt, das
  einem SpatialHash/Octree hinzugefuegt wird, wuerde PhysicsSystem NIE finden, da
  es nur scene.objects (den Object3D-Baum) durchlaeuft, nicht die raeumlichen
  Strukturen.

1.2 Die verschachtelte Broadphase-Schleife im Detail
--------------------------------------------------

Funktion: PhysicsSystem._resolveCollisions, src/physix/PhysicsSystem.ts:162-299.

Die eigentliche O(bodies x allColliders)-Doppelschleife steht in den Zeilen
174-294:

  174  for (let i = 0; i < bodies.length; i++) {         // aeussere: nur dynamische Bodies
  179    for (let j = 0; j < allColliders.length; j++) {  // innere: ALLE Collider

- Getestete Paare: body-vs-collider, wobei "collider" jedes kollidierbare Objekt
  mit bounds ist, dynamisch oder statisch (_collectCollidersRecursive,
  PhysicsSystem.ts:153-160). Der Durchlauf deckt also body-vs-static UND
  body-vs-body-Paare in einem Durchgang ab, mit allColliders als innerer Menge.

- Selbst-Ausschluss: if (dynObj === otherObj) continue; (Zeile 181).

- Doppel-Aufloesungs-Schutz fuer dynamisch-vs-dynamisch (Zeilen 183-185):

    const otherIdx = bodies.indexOf(otherObj);
    if (otherIdx !== -1 && otherIdx <= i) continue;

  Das ist ein Array.indexOf (O(n)) INNERHALB der inneren Schleife, was die
  gesamte Broadphase im schlimmsten Fall zu O(bodies x allColliders x bodies)
  macht - ein echter, im Hot-Path liegender Zusatzkostenpunkt, unabhaengig von der
  raeumlichen Struktur.

- Es gibt KEINEN vorgeschalteten Bounding-Sphere/Radius-Summen-Check im
  PhysicsSystem-Loop selbst. Die Schleife geht direkt vom index-basierten Schutz
  zum Typ-Dispatch (Zeilen 187-212, liest boundsA.type/boundsB.type direkt und
  ruft Collision.resolveSphereSphere / Collision.resolveSphereBox auf). Nur
  Collision.test() (hier NICHT verwendet, siehe 1.3) hat den
  Radius-Summen-Fruehausstieg; PhysicsSystem._resolveCollisions ruft
  Collision.test nicht auf, sondern direkt die resolveX-Funktionen, die jeweils
  sofort ihre eigene Narrowphase-Mathematik durchfuehren (also KEINE
  Broadphase-Vorfilterung ueberhaupt in diesem Pfad - genau deshalb wird eine
  Octree/SpatialHash-Broadphase gebraucht).

- In _resolveCollisions dispatchte Typen (Zeilen 192-212): nur Sphere-Sphere und
  Sphere-Box (beide Richtungen). BOX-BOX/OBB-OBB-PAARE WERDEN HIER GAR NICHT
  DISPATCHT - boundsA.type === 1 && boundsB.type === 1 hat keinen Zweig, also
  bleibt collisionFound false und Box-Box-Kollisionen werden von PhysicsSystem
  stillschweigend uebersprungen, obwohl Collision sie erkennen kann (siehe 1.3).

1.3 Collision.test — Signatur, Dispatch, erkannt-vs-aufgeloest
--------------------------------------------------

Signatur: public static test(a: BoundingVolume, b: BoundingVolume): boolean —
src/physix/Collision.ts:16.

Broadphase-Fruehausstieg INNERHALB von Collision.test selbst (Zeilen 17-19):

  const distSq: number = a.center.distanceToSq(b.center);
  const sumRad: number = a.getBroadRadius() + b.getBroadRadius();
  if (distSq > sumRad * sumRad) return false;

Das ist der EINZIGE existierende "billige Kugel-Summen"-Fruehausstieg im ganzen
Kollisions-Stack - er greift aber nur fuer Aufrufer von Collision.test, und
PhysicsSystem._resolveCollisions ruft Collision.test NIE auf (siehe 1.2), d.h.
DIESER FRUEHAUSSTIEG IST FUER DEN GAME-LOOP-PFAD AKTUELL TOT CODE. Er WIRD
verwendet von Octree.queryVolume (Octree.ts:170, 174) und SpatialHash.query
(SpatialHash.ts:82, ueber bounds.intersectsVolume(volume) ->
BoundingBox/BoundingSphere.intersectsVolume -> Collision.test, BoundingBox.ts:
163-165, BoundingSphere.ts:47-49).

Dispatch innerhalb von Collision.test (Zeilen 22-38), nach BoundingType
(src/enums/BoundingType.ts:6-13: SPHERE=0, BOX=1, OBB=2):

- Sphere-Sphere -> _sphereSphere (Zeilen 22-24, Impl. 130-134) — NUR ERKENNUNG,
  boolean.
- Box-Box -> _boxBox (Zeilen 25-27, Impl. 136-145) — NUR ERKENNUNG, einfacher
  AABB-Ueberlappungstest, boolean.
- Sphere-Box / Box-Sphere -> _sphereBox (Zeilen 28-33, Impl. 207-216) — NUR
  ERKENNUNG, boolean.
- OBB-OBB -> _obbObb (Zeilen 34-36, Impl. 151-182, vollstaendiges 15-Achsen-SAT
  ueber _testAxis, Zeilen 187-205) — NUR ERKENNUNG, boolean.
- Alles andere (Sphere-OBB, Box-OBB) faellt durch zu return false; (Zeile 38,
  bestaetigt durch Test "should gracefully handle unhandled collision
  permutations", tests/physix/Collision.test.ts:117-123).

Separate AUFLOESUNGS-Funktionen (liefern einen Korrekturvektor, nicht nur
boolean):

- Collision.resolveSphereSphere(s1, s2, result): boolean — Zeilen 104-128.
- Collision.resolveSphereBox(s, b, result): boolean — Zeilen 48-95.
- ES GIBT KEIN resolveBoxBox / resolveObbObb IRGENDWO IN Collision.ts.

Bestaetigte Kernaussage: Box-Box-Kollisionen werden von Collision.test/_boxBox
ERKANNT, aber von PhysicsSystem NIE AUFGELOEST. PhysicsSystems Dispatch-Block
(Zeilen 192-212) hat nur Zweige fuer (0,0) Sphere-Sphere und (0,1)/(1,0)
Sphere-Box; es gibt keinen (1,1) Box-Box- oder OBB-Zweig, also bleibt
collisionFound fuer diese Typ-Kombination false (Zeile 190, nie auf true gesetzt)
und das Paar wird stillschweigend ignoriert — keine Warnung, kein Event, keine
Korrektur. Konsistent damit, dass Collision.test's rein erkennende
_boxBox/_obbObb kein passendes resolve*-Gegenstueck hat. Zusammenfassung:
VOLLSTAENDIG AUFGELOEST = Sphere-Sphere, Sphere-Box (beide Reihenfolgen);
ERKANNT-ABER-VON-PHYSICSSYSTEM-UNGENUTZT = Box-Box, OBB-OBB; NIRGENDS ERKANNT =
Sphere-OBB, Box-OBB.

1.4 Bounding-Volume-Getter auf RigidBody/StaticCollider, Auto-Update
--------------------------------------------------

- RIGIDBODY SELBST HAT UEBERHAUPT KEINEN bounds/Bounding-Volume-Getter (komplett
  gelesen — nur Velocity/Force/Torque/Mass-Felder; kein bounds-Feld). Das
  Bounding-Volume liegt auf Object3D, nicht auf RigidBody: public bounds:
  BoundingVolume | undefined = undefined; (src/core/Object3D.ts:19, ueber
  implements Collidable, Object3D.ts:11, Collidable-Interface bei
  src/interfaces/Collidable.ts:7-10).

- STATICCOLLIDER exponiert es direkt: public bounds: BoundingVolume | undefined;
  (StaticCollider.ts:9), setzbar ueber Konstruktor (Zeilen 14-16). Ein dummer
  Datenhalter — nichts berechnet es automatisch neu; wer einen StaticCollider
  besitzt, muss .bounds selbst setzen (kein computeBounds() auf StaticCollider).

- Fuer Object3D (was PhysicsSystem tatsaechlich durchlaeuft) ist der
  Bounds-Getter billig zu LESEN (obj.bounds, ein plain Feld), aber NICHT
  automatisch von updateMatrixWorld() synchron gehalten. updateMatrixWorld()
  (Object3D.ts:169-179) berechnet nur localMatrix/worldMatrix rekursiv neu —
  ruehrt bounds NICHT an. Bounds werden nur durch einen expliziten, separaten
  Aufruf von computeBounds() aktualisiert (Object3D.ts:118-159), das die lokalen
  Geometrie-Bounds liest (this.geometry.getBoundingVolume(), Zeile 126) und
  .transform(this.worldMatrix) auf Box/Sphere aufruft (Zeilen 149, 155) — d.h.
  computeBounds() setzt voraus, dass worldMatrix bereits aktuell ist, also ist
  die korrekte Reihenfolge pro Frame: erst updateMatrixWorld(), dann
  computeBounds().

  PhysicsSystem.step() ruft beide in dieser Reihenfolge auf, aber NUR fuer
  Bodies in _bodies (dynamisch, Masse > 0): obj.updateMatrixWorld();
  obj.computeBounds(); (Zeilen 138-139), innerhalb der Pro-Body-Integrationsschleife
  (Zeilen 64-143).

  BOUNDS VON STATISCHEN COLLIDERN WERDEN VON PHYSICSSYSTEM NIE NEU BERECHNET —
  wenn sich ein "statisches" Objekt nach seinem initialen computeBounds()-Aufruf
  (irgendwo anders erledigt, z. B. Scene._addObjectToOctree bei Scene.ts:113 oder
  Test-Setup bei tests/physix/PhysicsSystem.test.ts:244-247, 276-279) bewegt/dreht,
  nutzt PhysicsSystem veraltete Bounds dafuer, da _resolveCollisions
  (Zeilen 162-299) niemals computeBounds()/updateMatrixWorld() auf
  allColliders-Eintraegen aufruft — es liest otherObj.bounds direkt (Zeile 188).
  Wichtig fuer den Entwurf einer raeumlichen Struktur: DIE STRUKTUR MUSS MIT
  BOUNDS AKTUALISIERT WERDEN, DIE NUR FUER DYNAMISCHE BODIES GARANTIERT FRISCH
  SIND, EINMAL PRO FRAME, NACH DER INTEGRATIONSSCHLEIFE.

  Zusatzbefund: Object3D.computeBounds() kehrt frueh mit this.bounds = undefined
  zurueck, wenn !this.isCollidable (Zeilen 119-122), und tut NICHTS (laesst
  veraltete bounds unangetastet), wenn !this.geometry (Zeile 124, kein
  else-Zweig) — ein Objekt ohne Geometrie, aber mit manuell zugewiesenen bounds
  (wie die Sphere-Test-Fixtures bei tests/physix/PhysicsSystem.test.ts:189, 197
  und ZeroAllocation.test.ts:18, 24) behaelt fuer immer, was manuell gesetzt
  wurde, da computeBounds() dafuer zum No-Op wird.

1.6 PhysicsSystem.step() — vollstaendige Ablaufstruktur
--------------------------------------------------

public step(scene: Scene, dt: number): void — src/physix/PhysicsSystem.ts:52-148.

  Guard (Zeile 53): if (dt <= 0) return; — frueher Ausstieg, keine Mutation bei
  nicht-positivem dt.

  1. Dynamische Bodies sammeln (Zeilen 55-61): bodies.length = 0 (Wiederverwendung
     von _bodies); rekursiver Scan von scene.objects ueber
     _collectBodiesRecursive (Zeilen 30-45) in bodies.

  2. Integration pro Body (Zeilen 63-143): Schleife for (const obj of bodies)
     (Zeile 64):
     - Schwerkraft anwenden (68-70)
     - acceleration = forces * inverseMass (73)
     - Semi-implizites Euler-Geschwindigkeits-Update v += a*dt (77-79)
     - Lineare Daempfung velocity *= friction (82)
     - Positions-Update p += v*dt (85-87)
     - Angular: angularAcceleration = torque * inverseInertia (91);
       angularVelocity += angularAcceleration*dt (94-96); Angular-Daempfung (99)
     - Quaternion-basierte Rotations-Integration, falls wLength > 1e-6 (102-134)
     - Weltmatrix + Bounds aktualisieren: obj.updateMatrixWorld();
       obj.computeBounds(); (138-139)
     - Kraefte/Drehmoment fuer naechsten Frame loeschen: rb.clearForces(); (142)

  3. Kollision (Broad+Narrow, Kommentar sagt "Here we will query the
     SpatialHash/Octree") (Zeilen 145-147): Kommentar an 145-146 markiert
     explizit diese Stelle als beabsichtigten Octree/SpatialHash-
     Integrationspunkt; ruft this._resolveCollisions(scene, bodies, dt); (147)
     auf.

     3a. Alle Collider sammeln (_resolveCollisions, 164-169):
         allColliders.length = 0; rekursiver Scan
         _collectCollidersRecursive (153-160) — DAS IST DIE "BROADPHASE" HEUTE,
         UND SIE IST WIRKLICH NUR "ALLES EINSAMMELN".

     3b. Verschachtelte Broad+Narrow-Phase (171-294): siehe 1.2 — direkte
         verschachtelte Schleife mit typbasiertem Narrowphase-Dispatch, keine
         raeumliche Partitionierung.

     3c. Aufloesung (Positionskorrektur + Impuls) pro gefundener Kollision
         (214-293): Sensor-Kurzschluss dispatcht nur ein Event, keine
         physische Reaktion (223-232); sonst Positionskorrektur nach
         Inverse-Masse-Verhaeltnis aufgeteilt (234-256); Impuls-/Bounce-
         Aufloesung mit Restitutions-Clamp fuer Ruhekontakte (257-285);
         Kollisions-Event-Dispatch unter Wiederverwendung von _collisionEvent
         (281-284).

  Cleanup (297-298): gepoolte result/rv-Vektoren an MathPool zurueckgeben.

  Nach der Kollisionsaufloesung folgt NICHTS mehr in step() — kein Post-Solve-
  Pass, kein Sleeping/Deaktivierungs-Schritt, keine separate Substep-Schleife;
  step() kehrt zurueck, sobald _resolveCollisions fertig ist.

2.3 Unterstuetzung fuer bewegte Objekte
--------------------------------------------------

KEINE VORHANDEN — nur Clear+Neu-Einfuegen des GESAMTEN Baums als einzige Strategie.

- Es gibt KEINE remove(obj)-Methode auf Octree oder OctreeNode (bestaetigt per
  vollstaendigem Lesen + repo-weitem Grep nach .remove( innerhalb von
  Octree.ts/SpatialHash.ts — keine Treffer). Der einzige Weg, ein Objekt zu
  "entfernen", ist clear() auf dem GESAMTEN Baum (Octree.ts:228-230 / 183-187),
  was ALLES loescht, nicht einen einzelnen Eintrag.
- Es gibt KEINE Update-Position-/Re-Index-Methode (kein updatePosition, move,
  reinsert usw. irgendwo in Octree.ts).
- Der EINZIGE Mechanismus, den die Codebase fuer bewegte Objekte verwendet, ist
  das Brute-Force-Muster in Scene.updateDynamicOctree() (Scene.ts:99-103): den
  GESAMTEN dynamischen Baum leeren und JEDES dynamische Objekt jeden Frame neu
  einfuegen. Das ist ein volles O(n)-Neu-Einfuegen (mit O(log n)-Abstieg
  jeweils) pro Frame, kein inkrementelles Update.
- Der statische Baum (staticOctree) ist explizit fuer statische Geometrie gebaut
  — er wird einmal befuellt (YadApp.ts:285) und nie wieder angefasst; nichts in
  src/ ruft updateStaticOctree() nach dem Start erneut auf, also wuerde der Baum
  stillschweigend veralten, wenn sich ein "statisches" Objekt bewegte (kein
  Codepfad, der das erkennt oder korrigiert).

Fazit: Der Octree ist FUNDAMENTAL eine Rebuild-from-scratch-Struktur. Er
unterstuetzt "bewegte Objekte" nur in dem groben Sinn, dass Scene.ts den
gesamten dynamischen Baum jeden Frame wegwirft und neu baut — es gibt kein
guenstiges Remove/Reinsert-per-Referenz-Primitiv ueberhaupt.

2.5 Weltgroesse — global, nicht regional; ausserhalb-der-Bounds wird stillschweigend verworfen
--------------------------------------------------

- Sowohl staticOctree als auch dynamicOctree werden mit einer einzigen festen
  Welt-Bounds-BoundingBox konstruiert, die einmal an Scene.initOctrees(bounds)
  uebergeben wird (Scene.ts:50-53), instanziiert in YadApp.ts:282-284 als

  mehrerer Octree-Instanzen irgendwo in src/.

  ein Objekt ausserhalb der Root-Box bewegt. Stattdessen liefert

  Objekt, das ausserhalb der festen Weltgrenzen abdriftet, einfach jeden Frame

  Broadphase-Wiederverwendung im Blick haben muss, falls die Physikwelt nicht
  garantiert innerhalb einer hartcodierten Box bleibt.

clear() (leert die gesamte Map, SpatialHash.ts:56).

Konsequenzen fuer die Nutzung dieser Klasse als PhysicsSystems Pro-Frame-
Broadphase fuer bewegte RigidBodies:

- Um ein bewegtes Objekt abzubilden, kann man es nicht "in-place bewegen"; man
  muss entweder (a) clear() dann insert() fuer jeden Collidable jeden Frame
  aufrufen — ein volles O(N)-Rebuild plus O(N*k)-Zell-Listen-Rebuild (k =
  durchschnittliche Zellen-pro-Objekt-Footprint), oder (b) selbst
  Remove-per-Zell-Logik ausserhalb der Klasse bauen (nicht exponiert; _grid ist
  privat), was die aktuelle API nicht unterstuetzt.
- insert()'s Pro-Zelle-list.includes(obj)-Dedup (SpatialHash.ts:45) ist O(Listen-
  laenge) pro beruehrter Zelle, also ist naives Neu-Einfuegen vieler dynamischer
  Bodies jeden Frame teurer als ein typisches Hash-Grid-Update (das einfach
  einen gespeicherten Zell-Key pro Objekt ueberschreiben und diffen wuerde).
- Praktisch: Diese Klasse unveraendert als PhysicsSystem.step()s Pro-Frame-
  Broadphase wiederzuverwenden (src/physix/PhysicsSystem.ts:52-148, das bereits
  jeden Body vor der Kollisionsaufloesung integriert, Zeilen 64-143 vs.
  Aufloesung bei Zeile 147), wuerde einen vollen clear()+re-insert()-alle-Pass
  jeden step()-Aufruf erfordern, d.h. kein inkrementeller/amortisierter Update-
  Pfad ist verfuegbar — es ist ein "jeden Frame von Grund auf neu bauen"-
  Kostenmodell, kein "alte Zelle entfernen / neue Zelle einfuegen"-Kostenmodell.

--------------------------------------------------
3.5 Query-Rueckgabesemantik
--------------------------------------------------

- query(volume) liefert Collidable[], gebaut aus einem Set<Collidable>
  (SpatialHash.ts:63, 83, 90) — ist also DEDUPLIZIERT ueber Zellen hinweg (ein
  Objekt, das mehrere Zellen ueberspannt, erscheint nur einmal im Ergebnis), und
  bereits NARROW-GEFILTERT: jeder Kandidat wird mit
  obj.bounds.intersectsVolume(volume) geprueft (SpatialHash.ts:82), bevor er
  hinzugefuegt wird — also nur echte Broadphase-UND-Narrowphase-bestehende
  Treffer, nicht rohe Zell-Inhalte.
- queryRay(ray, maxDistance) dedupliziert ebenfalls via Set (SpatialHash.ts:98,
  113, 118), FILTERT ABER NICHT NARROW — liefert jedes Objekt in jeder
  durchlaufenen Zelle entlang des abgetasteten Strahlpfads, ohne Pro-Objekt-
  Intersection-Test (Kontrast zu query()). Aufrufer (InteractionManager.ts:
  62-64) filtern dann selbst nach (isPickable), aber nicht nach echter
  Ray-Objekt-Intersection an dieser Stelle.
- Rueckgabewerte sind direkte Objektreferenzen (Collidable[]), keine
  Zell-/Bucket-Wrapper-Objekte — Aufrufer nutzen sie direkt (z. B.
  EnemyBehavior.ts:80-95 iteriert potentialHits und ruft
  Collision.resolveSphereSphere/Box direkt auf obj.bounds auf).

--------------------------------------------------
3.6 Kombination mit Octree / Allgemeinheit als Broadphase
--------------------------------------------------

- Scene haelt alle drei Strukturen nebeneinander, aber unabhaengig:
  staticOctree, dynamicOctree und spatialHash (src/core/Scene.ts:25-27). Kein
  Code verschmilzt sie oder referenziert sie ueber Kreuz — jede wird separat
  befuellt und abgefragt.
- Sie werden NUR an der Aufrufstelle kombiniert, nicht intern:
  InteractionManager.ts:54-71 und FirstPersonController.ts:164-169 und
  EnemyBehavior.ts:72-75 fragen jeweils UNABHAENGIG staticOctree, spatialHash
  und dynamicOctree ab und fuehren Ergebnisse auf Aufruferebene in einem Array/
  Set zusammen. PhysicsSystem.ts beruehrt bislang keine der beiden Strukturen —
  es macht aktuell Brute-Force-O(N*M)-Paarweise-Checks (_resolveCollisions,
  PhysicsSystem.ts:162-295, verschachtelte Schleife ueber bodies x allColliders
  bei Zeilen 174-179), nur mit einem TODO-Kommentar: PhysicsSystem.ts:146 —
  "// Here we will query the SpatialHash/Octree and resolve collisions via SAT."
- CHANGELOG.md:180-183 bestaetigt die urspruengliche Design-Absicht: SpatialHash
  wurde speziell hinzugefuegt "for O(1) grid-based collision broad-phase checks,
  highly optimized for large grid maps (like YAD)" und andere Systeme wurden
  "updated ... to seamlessly query the new SpatialHash" neben Octree — d.h. es
  wurde als YAD-Grid-spezifische Ergaenzung zu Octree entworfen, nicht als
  Drop-in-Ersatz fuer eine allgemeine 3D-Broadphase.
- Angesichts der Punkte 3.2 und 3.4 (keine Y-Partitionierung, keine
  inkrementelle Bewegungsunterstuetzung, unbegrenzte Map<string, Collidable[]>
  ohne Welt-Bounds-/Kapazitaetsgrenzen) ist SpatialHash nur fuer Szenen als
  allgemeine Broadphase wiederverwendbar, in denen (a) Objekte einigermassen
  gleichmaessig ueber die XZ-Ebene verteilt sind, in einer Groessenordnung nahe
  cellSize, und (b) der Inhalt weitgehend statisch ist oder selten neu gebaut
  wird. Es ist, so wie geschrieben, KEINE allgemeine 3D-dynamische-Broadphase —
  es braeuchte eine Y- (oder volle 3D-) Achse in _getKey/insert/query, plus
  eine Remove-/Re-Key-API, um PhysicsSystems Pro-Frame-bewegte-RigidBody-
  Anwendungsfall sicher zu bedienen, ohne volle Szenen-Rebuild-Kosten jeden Tick.
